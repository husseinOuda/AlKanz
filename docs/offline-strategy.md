# استراتيجية العمل دون اتصال

## الفصل الأساسي

| الطبقة | ما تحتويه | من يديرها |
|---|---|---|
| **Cache Storage** | أصول التطبيق: HTML, CSS, JS, أيقونات, manifest | `sw.js` |
| **IndexedDB** | بيانات العمل: منتجات، فواتير، عملاء، مصروفات، حركات | التطبيق |

`sw.js` **لا يلمس IndexedDB إطلاقاً**، والتطبيق لا يلمس Cache Storage. تحديث التطبيق
يستبدل الأصول ولا يمسّ البيانات؛ استعادة نسخة احتياطية تستبدل البيانات ولا تمسّ الأصول.

---

## وضعان للتشغيل

| | `index.html` مباشرة (`file://`) | خادم محلي / HTTPS |
|---|---|---|
| كل الوظائف والبيانات | ✅ IndexedDB متاح والسياق آمن | ✅ |
| Service Worker وتخزين الأصول | ❌ يرفضه المتصفح على `file://` | ✅ |
| التثبيت كتطبيق (PWA) | ❌ | ✅ |
| طلب تخزين دائم | ❌ | ✅ |

في وضع `file://` لا حاجة إلى تخزين مؤقت للأصول أصلاً — الملفات على القرص مباشرةً،
ولا توجد شبكة يمكن أن تنقطع. «العمل دون اتصال» مُحقَّق بداهةً، لكن بلا مزايا PWA.

Service Worker **لا يعمل من `file://`**، وهذا قيد متصفح لا يمكن تجاوزه.

التطبيق يكشف هذا صراحةً بدل الادعاء:

```js
// src/services/pwa.js
export function offlineCapability() {
  // Chrome يعتبر file:// سياقاً آمناً (isSecureContext === true) لكنه يرفض
  // تسجيل Service Worker عليه، لذا نفحص البروتوكول صراحةً.
  if (window.location.protocol === 'file:') {
    return { ok: false, status: 'file', message: '…كل الوظائف والبيانات تعمل بالكامل، لكن…' };
  }
  if (!('serviceWorker' in navigator)) return { ok: false, status: 'unsupported', … };
  if (!window.isSecureContext)        return { ok: false, status: 'insecure', … };
  return { ok: true, status: 'ok', message: '' };
}
```

النتيجة تظهر في شاشة الإعدادات (بطاقة «حالة التطبيق»). في وضع `file://` **لا يظهر إنذار**
لأن الوضع مدعوم بالكامل — يظهر فقط توضيح لما هو غير متاح.

### كيف يعمل وضع `file://`

المتصفح يحجب وحدات ES عبر `file://` (CORS، `origin 'null'`)، لكنه يسمح بالسكربتات
الكلاسيكية. لذلك `src/boot-guard.js` — وهو سكربت كلاسيكي — يفحص البروتوكول ويحمّل:

- `file://` ⇒ `app.bundle.js` (حزمة كلاسيكية مُولَّدة بـ `node tools/build.mjs`)
- `http(s)` ⇒ `src/app.js` (وحدات ES أصلية، بلا بناء)

كما يحقن `<link rel="manifest">` و`preload` الخطوط في وضع الخادم فقط، لأن جلبهما عبر
`file://` يفشل بخطأ CORS بلا فائدة.

## استراتيجيات التخزين المؤقت

### التنقّل (`request.mode === 'navigate'`) — الشبكة أولاً بمهلة

```
navigation preload → إن توفّر: استخدمه وحدّث الكاش
                   → وإلا: fetch بمهلة 3 ثوانٍ
                          → نجح: أعده وحدّث الكاش
                          → فشل/انتهت المهلة: index.html من الكاش
                          → لا يوجد كاش: صفحة "غير متصل" واضحة
```

**لماذا الشبكة أولاً هنا:** المستخدم المتصل يحصل على أحدث نسخة فوراً، والمنقطع يحصل على
هيكل التطبيق من الكاش خلال 3 ثوانٍ كحد أقصى. لو عكسنا (كاش أولاً) لظلّ المستخدم على نسخة
قديمة حتى يتدخّل Service Worker جديد.

### الأصول (JS/CSS/أيقونات) — الكاش أولاً

كل الأصول مخزّنة مسبقاً في `install`. أي تغيير في أصل يعني إصدار كاش جديداً، فلا حاجة
لسؤال الشبكة. أصل غير موجود دون اتصال يرجع `504` صريحاً بدل استجابة فارغة صامتة.

### طلبات خارج الأصل (Origin)

لا يتدخّل فيها Service Worker إطلاقاً. التطبيق لا يصدر أي طلب خارجي أصلاً —
CSP يمنع ذلك (`connect-src 'self'`).

## التخزين المسبق المرن

```js
const results = await Promise.allSettled(
  SHELL_ASSETS.map((asset) => cache.add(new Request(asset, { cache: 'reload' })))
);
```

`cache.addAll()` تفشل كلياً إذا فشل أصل واحد، فيبقى التطبيق بلا أوفلاين بسبب ملف واحد.
`Promise.allSettled` يخزّن ما نجح ويسجّل ما فشل في الطرفية. `cache: 'reload'` يتجاوز
كاش HTTP فلا تُخزَّن نسخة قديمة.

## دورة حياة التحديث

```
1. المستخدم يفتح التطبيق
2. المتصفح يكتشف sw.js مختلفاً بالبايت
3. النسخة الجديدة تُثبَّت (install) وتنتظر في حالة "waiting"
4. updatefound + statechange === 'installed' + وجود controller
   ⇒ appState.updateAvailable = true
5. يظهر إشعار "تحديث متاح" فيه زر "تحديث الآن" (ونفس البطاقة في الإعدادات)
6. المستخدم ينقر ⇒ postMessage({ type: 'SKIP_WAITING' })
7. العامل الجديد يتولّى ⇒ controllerchange ⇒ إعادة تحميل مرة واحدة
```

**لا تحديث تلقائي.** إعادة التحميل الفورية قد تقطع فاتورة قيد الإعداد أو نموذجاً غير
محفوظ. القرار للمستخدم.

في `activate` تُحذف كل الكاشات التي تبدأ بـ `sales-` ولا تطابق الإصدار الحالي.

## ما يعمل دون اتصال

**كل شيء.** التطبيق لا يحتاج الشبكة لأي وظيفة:

- البيع الكامل وإتمام الفواتير وطباعتها.
- إضافة وتعديل المنتجات والعملاء والمصروفات.
- تسويات المخزون والجرد.
- كل التقارير والفلاتر.
- استيراد وتصدير Excel (المعالجة كلها في المتصفح).
- النسخ الاحتياطي والاستعادة.

هذا يتجاوز ما تقدّمه المنتجات السحابية أوفلاين: Square يحدّ الأوفلاين بـ 24 ساعة وسقف
مبلغ للمعاملة، وLoyverse لا يعرض مستويات المخزون ولا يسمح بالمرتجعات أوفلاين
(المصادر في [`competitive-benchmark.md`](competitive-benchmark.md)). نحن لا نواجه هذه
القيود لأننا لا نعالج بطاقات ولا نزامن مع خادم — وهذا هو التنازل المقابل.

اختبار E2E آلي يقطع الشبكة عبر CDP ثم يعيد تحميل التطبيق ويتحقق من رسم الهيكل والجدول
وقراءة البيانات المحلية.

## حالة الاتصال في الواجهة

`navigator.onLine` مراقَب عبر حدثي `online`/`offline`، وتظهر الحالة في الشريط العلوي:

- **متصل** ⇒ «جاهز دون اتصال» (أخضر) — رسالة طمأنة أن الأوفلاين مفعّل.
- **غير متصل** ⇒ «غير متصل — يعمل محلياً» (كهرماني).

**لا تُعطَّل أي وظيفة في الحالتين.** الشارة إعلامية فقط.

## التخزين والبقاء

### تقدير المساحة

`navigator.storage.estimate()` يعطي `usage` و`quota`، ويُعرضان في الشريط الجانبي
وشاشتَي الإعدادات والنسخ الاحتياطي.

### التخزين الدائم

`navigator.storage.persist()` يطلب من المتصفح ألا يحذف البيانات تلقائياً عند ضغط المساحة.
حسب [MDN](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist):
- يتطلب سياقاً آمناً.
- يرجع `Promise<boolean>` — والمتصفح قد يرفض.

**يُطلب بعد نقرة صريحة من المستخدم فقط** (زر في الإعدادات أو في «إجراءات التعافي»)،
لا تلقائياً عند الإقلاع. عند الرفض تُعرض رسالة صريحة تربط ذلك بضرورة النسخ الاحتياطي.

### حدود البقاء — بصراحة

| الحدث | النتيجة |
|---|---|
| إغلاق المتصفح وإعادة فتحه | ✅ البيانات باقية |
| إعادة تشغيل الجهاز | ✅ باقية |
| فتح التطبيق من نطاق (Origin) آخر | ❌ قاعدة بيانات مختلفة تماماً |
| فتح التطبيق من متصفح آخر | ❌ لا توجد بيانات |
| «مسح بيانات التصفح» | ❌ **تُفقد كل البيانات نهائياً** |
| وضع التصفح الخفي | ❌ تُمسح عند إغلاق النافذة |
| ضغط مساحة القرص بلا تخزين دائم | ⚠️ قد يحذف المتصفح البيانات |

لهذا السبب **النسخ الاحتياطي مسؤولية تشغيلية أساسية لا ميزة إضافية**، والتطبيق يذكّر بها
دورياً (يومي/أسبوعي حسب الإعداد).

## قائمة فحص النشر

1. انشر على **HTTPS** (أو `http://localhost` للتجربة).
2. تأكد أن `sw.js` يُقدَّم من جذر النطاق أو أن ترويسة `Service-Worker-Allowed` تسمح بالنطاق المطلوب.
3. تأكد من نوع MIME الصحيح لـ `.webmanifest` (`application/manifest+json`).
4. **لا تضع كاش HTTP طويل الأمد على `sw.js`** — وإلا لن يصل التحديث للمستخدمين.
   الأصول ذات البصمة يمكن تخزينها طويلاً.
5. أضف ترويسة `Content-Security-Policy` بها `frame-ancestors 'none'`
   (لا تعمل عبر `<meta>` — انظر [`security-review.md`](security-review.md)).
6. افتح التطبيق مرة واحدة متصلاً قبل الاعتماد عليه أوفلاين.
