# ميزات تحتاج Backend

كل ميزة هنا **غير منفّذة**، ولم تُحاكَ في الواجهة بأي شكل. لا يوجد في التطبيق زر أو شاشة
توحي بوجود مزامنة أو حسابات أو صلاحيات.

الترتيب حسب القيمة العملية لمتجر تجزئة صغير.

---

## 1. المزامنة بين الأجهزة

**لماذا لا تعمل محلياً:** IndexedDB معزول لكل نطاق (Origin) ومتصفح. لا توجد أي واجهة
متصفح تسمح لجهازين بمشاركة قاعدة بيانات محلية. أي «مزامنة» بلا خادم ستكون خدعة.

**العقد المقترح:**

```http
POST /api/sync
Authorization: Bearer <token>
Content-Type: application/json

{
  "deviceId": "dev_...",
  "since": "2026-08-04T10:00:00Z",
  "changes": [
    { "store": "sales", "op": "put", "id": "sal_...",
      "updatedAt": "...", "version": 3, "payload": { ... } }
  ]
}
```

```json
{
  "serverTime": "2026-08-04T10:05:00Z",
  "changes": [ /* ما تغيّر على الخادم منذ since */ ],
  "conflicts": [
    { "store": "products", "id": "prd_...", "resolution": "server-wins",
      "server": { ... }, "client": { ... } }
  ]
}
```

**قرارات التصميم المطلوبة قبل التنفيذ:**
- **الفواتير غير قابلة للتغيير** ⇒ إضافة فقط، لا تعارض ممكن. المزامنة بسيطة.
- **المخزون تراكمي** ⇒ لا تُزامن `product.quantity` (قيمة مطلقة تتضارب)، بل تُزامن
  **حركات المخزون** ويُعاد حساب الكمية على الخادم. `inventoryMovements` مصمَّم لهذا أصلاً.
- **المنتجات والعملاء** ⇒ آخر كتابة تفوز، مع `version` للكشف عن التعارض وعرضه للمستخدم.
- **ترقيم الفواتير** ⇒ لا يمكن أن يبقى عدّاداً محلياً. يحتاج بادئة لكل جهاز
  (`INV-A-2026-00001`) أو حجز نطاقات من الخادم.

**التغيير المطلوب على النموذج الحالي:** إضافة `updatedAt` و`version` و`deviceId` لكل سجل،
وسجل `pendingChanges` محلي. النموذج الحالي جاهز جزئياً (`updatedAt` موجود).

## 2. تعدد المستخدمين والصلاحيات

**لماذا لا تعمل محلياً:** أي فحص صلاحية في JavaScript يمكن تجاوزه من أدوات المطوّر.
PIN محلي **ليس مصادقة** — تفصيل الرفض في [`security-review.md`](security-review.md) §7.1.

**العقد المقترح:**

```http
POST /api/auth/login   { "email": "...", "password": "..." }
→ { "accessToken": "...", "refreshToken": "...",
    "user": { "id": "...", "name": "...", "role": "cashier" } }
```

| الدور | الصلاحيات |
|---|---|
| `owner` | كل شيء + الإعدادات + حذف البيانات |
| `manager` | كل العمليات + التقارير، بلا حذف بيانات |
| `cashier` | البيع وقراءة المنتجات فقط، بلا تقارير ولا تكاليف |
| `stock` | المخزون والتسويات فقط |

**الأثر:** كل عملية حسّاسة تُتحقَّق **على الخادم**. الواجهة تخفي ما لا يُسمح به لتحسين
التجربة فقط، لا كإجراء أمني.

**ما ينفتح معه:** تدقيق حقيقي — `inventoryMovements.actor` يصبح معرّف مستخدم حقيقياً بدل
«المستخدم»، فيمكن معرفة **من** نفّذ كل حركة.

## 3. فروع ومستودعات متعددة

**لماذا لا تعمل محلياً:** تتطلب مصدر حقيقة واحداً لمستوى المخزون عبر مواقع.

**العقد المقترح:**

```http
GET  /api/locations
GET  /api/inventory?locationId=loc_...
POST /api/transfers   { "from": "loc_a", "to": "loc_b",
                        "lines": [{ "productId": "...", "quantity": 10 }] }
```

**التغيير المطلوب:** `locationId` على `products.quantity` (يصبح جدول مخزون منفصل
`stockLevels: { productId, locationId, quantity }`) وعلى `sales` و`inventoryMovements`.
تغيير جوهري في النموذج.

---

## 4. الورديات وصناديق النقد

**لماذا لا تعمل محلياً بمعنى مفيد:** الوردية تربط الكاشير بجهاز وفترة زمنية. بلا مستخدمين
تصبح مجرد ختم زمني بلا قيمة رقابية.

**العقد المقترح:**

```http
POST /api/shifts/open   { "openingCashMinor": 50000 }
POST /api/shifts/close  { "countedCashMinor": 187500 }
→ { "expectedMinor": 188000, "differenceMinor": -500, "salesMinor": 138000, ... }
```

**يعتمد على:** الميزة رقم 2.

---

## 5. معالجة مدفوعات البطاقات

**لماذا لا تعمل محلياً — ولن تُنفَّذ محلياً أبداً:** معالجة البطاقات تتطلب التزام PCI DSS
واتصالاً مؤمَّناً بمزوّد دفع. **لا يجوز أن تمرّ بيانات بطاقة عبر تطبيق محلي بلا خادم.**

**النهج الصحيح:** تكامل مع طرفية دفع (Terminal SDK) أو مزوّد يعيد رمزاً (token)،
**دون أن تلمس بيانات البطاقة تطبيقنا إطلاقاً**.

الحالة الآن: التطبيق يسجّل «طريقة الدفع» كتصنيف محاسبي فقط (نقدي/بنكي/بطاقة/شيك)،
ولا يخزّن أي رقم بطاقة أو رمز تحقق. هذا لن يتغير.

---

## 6. أوامر الشراء والموردون

**لماذا أُجّلت:** ليست مستحيلة محلياً، لكنها تضيف كيانين (`Supplier`, `PurchaseOrder`)
ودورة حياة كاملة (مسودة → مرسل → مستلم جزئياً → مستلم) لا تظهر في أي شاشة مرجعية.

**العقد المقترح إن نُقلت للخادم:**

```http
POST /api/purchase-orders
GET  /api/purchase-orders?status=pending
POST /api/purchase-orders/:id/receive
     { "lines": [{ "productId": "...", "receivedQuantity": 8 }] }
```

الاستلام يولّد حركات مخزون من نوع `in` بسبب «شراء جديد» — وهو مسار موجود ومختبَر
في النموذج الحالي.

---

## 7. الفوترة الإلكترونية (ZATCA / e-invoicing)

**لماذا لا تعمل محلياً:** تتطلب شهادة رقمية وختماً تشفيرياً وإرسالاً لمنصة الجهة التنظيمية.
المفتاح الخاص لا يجوز أن يوجد في متصفح.

**ما هو جاهز في النموذج الحالي:** `storeTaxNumber` و`storeCrNumber` وتفصيل الضريبة
لكل فاتورة وتجميد `taxRateBp` تاريخياً. ما ينقص هو التوقيع والإرسال — كلاهما مسؤولية خادم.

---

## 8. تقارير عبر فترات طويلة جداً

**الحد الحالي:** التقارير تقرأ عبر فهرس `dayKey` وتجمّع في الذاكرة. مع عشرات آلاف
الفواتير سيصبح تقرير سنة كامل بطيئاً.

**غير عاجل:** متجر صغير ينتج ~50 فاتورة يومياً = ~18 ألف سنوياً، وهو حجم يعمل بسلاسة.

**عندما يصبح عاجلاً:** تجميعات مسبقة يومية/شهرية على الخادم، أو متجر `dailyAggregates`
محلي يُحدَّث عند كل بيع.

---

## ما لن يُنقل إلى Backend

| الميزة | لماذا تبقى محلية |
|---|---|
| البيع نفسه | يجب أن يعمل دون اتصال — هذا جوهر المنتج |
| قراءة المنتجات والمخزون | نفس السبب |
| الطباعة | محلية بطبيعتها |
| استيراد وتصدير Excel | معالجة كاملة في المتصفح، بلا رفع ملفات |
| النسخ الاحتياطي المحلي | يبقى كخيار حتى مع وجود مزامنة سحابية |

## ملخص المسار

```
المرحلة الحالية: محلي بالكامل، جهاز واحد
   ↓ (تعدد المستخدمين والصلاحيات — §2)
مصادقة حقيقية وتدقيق باسم المستخدم
   ↓ (المزامنة — §1)
عدة أجهزة على نفس المتجر
   ↓ (الفروع — §3)
عدة مواقع
   ↓ (الورديات §4، أوامر الشراء §6، الفوترة الإلكترونية §7)
نظام تجزئة كامل
```

كل مرحلة تعتمد على ما قبلها. تنفيذ الفروع قبل المصادقة، مثلاً، ينتج نظاماً بلا رقابة.
